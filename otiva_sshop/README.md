# Уведомления менеджеров о сообщениях клиентов из Avito
Сервис обработки входящих сообщений из Avito, который отправляет менеджерам email-уведомления о непрочитанных сообщениях и собирает бизнес-метрики, связанные с обработкой обращений клиентов.

Основная цель — снизить вероятность пропуска клиентских сообщений и сделать нагрузку менеджеров измеримой.

## Основные возможности
- **Email-уведомления:** отправка менеджеру уведомлений о непрочитанных сообщениях клиентов.
- **Учёт Response Lag:** измерение времени реакции менеджера на клиентские обращения.
- **Распределение нагрузки:** закрепление клиентов за менеджерами и учёт количества закреплённых клиентов.
- **Обработка разных сценариев:** поддержка зарегистрированных клиентов и новых пользователей, обратившихся через Avito.
- **Многопоточная обработка:** подготовка и пакетная отправка уведомлений через Celery и Redis.
- **Обработка ошибок отправки:** повторные попытки при определённых ошибках SMTP.
- **Сбор бизнес-метрик:** обновление данных даже в случаях, когда отправка email не требуется.


## Архитектура
Основная логика реализована в Django-приложении `chat`.

```
flowchart TD
    A[Avito Webhook] --> B[Валидация сообщения]
    B --> C[Подготовка задачи]
    C --> D[Celery + Redis]
    D --> F[Аутентификация и авторизация]
    F --> G[Обновление бизнес-метрик]
    G --> H{Сообщение прочитано?}
    H -->|Да| I[Завершение без email]
    H -->|Нет| J[Подготовка email]
    J --> K[SMTP Яндекса]
    K --> L{Результат отправки}
    L -->|Успех| M[Завершение обработки]
    L -->|Временная ошибка| N[Retry-очередь]
```


## Обработка входящего сообщения можно разделить на 3 этапа:
### 1. Приём и первичная обработка
- Django принимает входящие события через webhook.
- Выполняется первичная валидация сообщения.
- Подготовка уведомлений выносится в асинхронную обработку, чтобы не привязывать ответ webhook к длительности отправки email.
- Для определения Response Lag используются данные об активных чатах и состоянии обработки обращений.


### 2. Подготовка уведомлений
- Сообщения обрабатываются пакетами с ограничением количества сообщений из одного чата.
- Выполняются проверки пользователя и необходимые операции аутентификации и авторизации.
- Определяются данные клиента, менеджера и получателя уведомления.
- Бизнес-метрики обновляются независимо от необходимости отправки email.
- Если сообщение уже прочитано менеджером, email не отправляется.


### 3. Отправка email
- Уведомления подготавливаются на основе данных сообщения.
- Отправка выполняется через SMTP-сервер Яндекса.
- Для временных ошибок SMTP предусмотрен механизм повторных попыток.



## Ключевые технические решения

### Асинхронная обработка webhook
Отправка email вынесена из синхронного пути обработки входящего события. Это позволяет не связывать время ответа webhook с доступностью SMTP-сервера и скоростью отправки уведомлений.

### Пакетная обработка
Сообщения группируются для отправки с использованием механизма блокировки `lock_key` и ограничений на количество сообщений из одного чата. Это позволяет контролировать размер обрабатываемых пакетов и нагрузку на систему.

### Разделение бизнес-логики и уведомлений
Не каждое входящее сообщение должно приводить к отправке email, но обработка сообщения может влиять на бизнес-метрики. Поэтому обновление метрик и принятие решения об отправке уведомления рассматриваются как отдельные этапы.

### Управление очередями и восстановление после ошибок
В реализации используются очереди `pending` и `processing`, а также повторные попытки отправки при определённых ошибках SMTP.

При этом корректность восстановления после падения воркера зависит от реализации перемещения сообщений между очередями, подтверждения задач и повторной обработки. Эти гарантии необходимо оценивать по фактическому коду и тестам.

## Бизнес-логика и метрики

### Response Lag
Response Lag отражает время реакции менеджера на клиентское обращение.
- Отсчёт начинается с первого сообщения, оставшегося без ответа менеджера.
- Метрика фиксируется при ответе менеджера клиенту.
- Данные используются для анализа своевременности обработки обращений.


### Учёт нагрузки менеджеров
Нагрузка определяется количеством клиентов, закреплённых за менеджером, а не количеством открытых чатов с этими клиентами. Это позволяет учитывать одного клиента как одну единицу нагрузки, даже если с ним существует несколько чатов разных типов.

### Обработка новых и существующих клиентов
Поддерживаются сообщения от клиентов, уже зарегистрированных на сайте, и от новых пользователей, которые впервые связались с магазином через Avito.

## Требования
Для локального запуска необходимы:
- Docker и Docker Compose.
- Доступ к SMTP Яндекса и учётные данные отправителя.
- Адреса электронной почты менеджеров.
- Настроенное окружение приложения.

## Локальный запуск

### 1. Настройка окружения
Создайте `.env` на основе конфигурации, используемой в `compose-dev.yml`.
Пример структуры:

```.env
DEBUG=True
SECRET_KEY=<dev-secret-key>
ALLOWED_HOSTS=localhost,127.0.0.1
LOG_LEVEL=INFO

POSTGRES_DB=<database-name>
POSTGRES_USER=<database-user>
POSTGRES_PASSWORD=<database-password>
POSTGRES_PORT=5432

REDIS_PORT=6379
REDIS_PASSWORD=<redis-password>

AVITO_STORE_ID=<avito-store-id>
ROOT_EMAIL=<sender-email>
EMAIL_PASSWORD=<smtp-app-password>
```

Значения должны соответствовать конфигурации Docker Compose. 
Для SMTP используйте необходимые учётные данные, а также пароль уникальный пароль для вашей почты для SMTP сервера Яндекса.

### 2. Запуск контейнеров
```sh
docker compose -f compose-dev.yml up
```

### 3. Создание суперпользователя

Откройте shell контейнера Django:
```sh
docker exec -it django-app sh
```

Внутри контейнера выполните команду Django для создания суперпользователя:
```sh
python manage.py createsuperuser
```
Команду необходимо выполнять из каталога, в котором доступен `manage.py`.

### 4. Создание тестовых менеджеров

Откройте административную панель:
`http://localhost:8000/admin/`

Создайте двух тестовых менеджеров с ID `11111` и `21111`, заполнив обязательные поля модели.

Эти ID используются только в примере настройки локального окружения.

### 5. Настройка данных в Redis
Подключитесь к Redis:

```
redis-cli -a <redis-password>
```

Добавьте адреса получателей:

```
HSET emails_managers 11111 <manager-1-email>
HSET emails_managers 21111 <manager-2-email>
```

Инициализируйте данные менеджеров:
```
HSET managers 11111 0
HSET managers 21111 0
```

Эти команды соответствуют описанной конфигурации локального окружения. Структуру ключей и значения необходимо сверить с фактической реализацией.

### 6. Проверка webhook

Отправьте POST-запрос на endpoint `/webhook/`, имитирующий событие входящего сообщения Avito.

Пример минимальной структуры запроса:

```json
{  
  "id": "event-id",  
  "payload": {  
    "type": "message",  
    "value": {  
      "author_id": 22234,  
      "chat_id": "test-chat-id",  
      "chat_type": "u2i",  
      "content": {  
        "call": None,  
        "text": "Привет!"  
      },  
      "created": 1760000000,  
      "id": "message-id",  
      "item_id": 124453,  
      "read": None,  
      "type": "text",  
      "user_id": 123  
    }  
  },  
  "timestamp": 1760000000,  
  "version": "v1.1"  
}
```

Это иллюстративный пример структуры события. Перед отправкой убедитесь, что обязательные поля соответствуют валидатору webhook и ожидаемому формату Avito API.

После отправки проверьте:

1. Приём и обработку сообщения.
2. Обновление данных в PostgreSQL и Redis.
3. Отправку email, если сообщение подходит под условия уведомления.
4. Поведение при повторной обработке и ошибках SMTP.

Для наблюдения за задачами Celery и состоянием Redis используйте инструменты, настроенные в `compose-dev.yml`, включая Flower и RedisInsight

## Тестирование

Функциональность покрыта юнит- и интеграционными тестами с использованием `pytest`. End-to-end сценарии проверяются вручную.

При проверке рекомендуется отдельно рассматривать:
- обработку новых и существующих клиентов;
- сообщения, уже прочитанные менеджером;
- фиксацию Response Lag;
- пакетную отправку сообщений;
- ошибки SMTP и повторные попытки;
- поведение при повторном получении одного события.

## Известные ограничения

При падении воркера во время обработки чата с количеством сообщений, превышающим установленный лимит `max_count`, часть сообщений сверх лимита может не сохраниться в базе данных.

### Технические преимущества и дополнения:  
  
Преимущества на стороне endpoint:  
1. Отправка сообщений происходит "внутри" приложения, в связи с чем дублирование сообщений исключено.  
   Ограничение API соблюдается(resp 200 в течение 2сек) и не зависит от процесса отправки уведомления менеджеру  
2. Проверки на достоверность пользователя, учитывается статус создания пользователя  
3. Активные чаты кэшируются для определения response_lag  
  
Преимущества на стороне отправки уведомлений  
4. Отправка сообщений менеджеру пачкой (lock_key)  
5. Учитываются болезни Celery (pending и processing очереди уведомлений), в связи с чем практически полностью достигается exatly-one-delivery (повторная отправка уже отправленного уведомления может произойти только если воркер умер до того как почистились pending, но после отправки писем по smtp).   
6. Сообщения из pending перетекают в processing; processing <= pending  
7. Пред-подготовка emails_ids  
8. Сохраняется история emails, в связи с чем переписка с клиентом в одной истории emails на почте менеджера  
9. Каждое уведомление обновляет данные в бд, но не каждое должно быть отправлено менеджеру
